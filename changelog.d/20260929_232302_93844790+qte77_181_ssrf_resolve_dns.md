### Security

- SSRF guard (`utils/_ssrf.py`, shared by `utils.discovery`, `utils.sitemap` and the
  `easter_hunt` contrib) is now **escalation-only** (owner decision, 2026-09-30): the
  seed a caller passes in — `discover(url)`'s argument, the sitemap `domain`, each
  `hunt()` seed — is **never blocked**, including a literal internal IP or
  `localhost`; pointing these utils at a local dev server is intentional and
  supported. Only a URL the tool **derives** from that seed (a probed path, a
  redirect target) is checked, and only when the seed itself is **external**: an
  internal seed means the caller already trusts everything reachable from it, so
  nothing derived from it is checked either. `is_seed_internal(seed)` computes that
  verdict once per `discover()`/`fetch_sitemap_urls()`/`hunt()`-per-seed run.
  ([#181](https://github.com/qte77/polyfetch-scrape/issues/181))
- When the seed is external, a derived hostname is **resolved**, and every A/AAAA
  answer must be external: `localhost`, an internal DNS name, a name pinned to a
  cloud metadata address (`169.254.169.254`), and a name that mixes one public answer
  with an internal one are all rejected before any connection. "Internal" is an
  **allowlist**, not named ranges: an address is internal unless `ipaddress`'s
  `is_global` says it is globally routable, or it is multicast (checked explicitly —
  some multicast ranges report `is_global` too). This also closes a gap the named-flag
  check missed: shared/CGNAT address space (RFC 6598, `100.64.0.0/10`), which hosts
  real cloud metadata endpoints, e.g. Alibaba Cloud's `100.100.100.200`. Literal IPs
  (IPv4, IPv6, and IPv4-mapped IPv6 literals like `::ffff:127.0.0.1`) are judged the
  same way and short-circuit the resolver. A derived name that does not resolve
  passes through — fail-open, because the HTTP client cannot connect to an address
  that does not exist either. ([#181](https://github.com/qte77/polyfetch-scrape/issues/181))
- New `check_redirect(requested_url, response, *, seed_is_internal)` applies the same
  escalation-only rule to **redirect targets** — the URL a response landed on (the
  `curl_cffi` and browser tiers follow redirects themselves) and an unfollowed
  301/308 `Location` — so an external seed can no longer be bounced onto an internal
  address via a redirect. Wired into every guarded call site; raises `ValueError`
  (not `FetchError`), so a caller that swallows fetch failures still surfaces the
  block. **Known limit:** the check is preventive on `httpx` (which does not follow
  redirects itself, so the unfollowed `Location` is checked before any connection),
  but post-hoc on `curl_cffi` (`allow_redirects` defaults to `True`) and the
  Patchright/browser tier (`page.goto` always follows) — those two have already
  connected to the redirect target by the time the check runs; it still stops the
  response body from reaching the caller.
  ([#181](https://github.com/qte77/polyfetch-scrape/issues/181))

### Changed

- **Relaxed, not tightened, relative to the previous guard:** a literal internal-IP
  seed used to be rejected outright (`discover("http://127.0.0.1")` raised
  `ValueError`); it is now always allowed — the guard only ever gates what the tool
  derives from an *external* seed. `fetch()` itself remains unguarded either way,
  preserving the "fetch any URL" contract. DNS rebinding remains out of scope —
  mitigating it needs pinned-IP connect, which none of the tiers expose (tracked as
  a follow-up issue).
